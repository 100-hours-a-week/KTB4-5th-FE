# 요청·응답 공통 포맷 설계

## 최종 제안

- 요청은 API별 JSON DTO를 직접 전달한다.
- 성공 응답은 `code`, `message`, `data`를 포함하는 `ApiResponse<T>`로 통일한다.
- 오류 응답은 RFC 9457(`application/problem+json`) 구조를 사용한다.
- 오류 응답에는 서비스 고유 식별자인 `code`를 확장 필드로 추가한다.
- 서비스 코드는 `DOMAIN-HTTP-NNN` 형식으로 관리한다.

## 1. JSON:API 검토

JSON:API는 단순히 응답을 `data`로 감싸는 규칙이 아니라, 리소스 표현·조회·수정·관계·오류 처리까지 정의하는 규격이다.

| 규칙 | 제공하는 이점 |
| --- | --- |
| `type`, `id`, `attributes` | 서로 다른 종류의 데이터를 동일한 구조로 식별하고 처리 |
| `relationships`, `included` | 관련 데이터를 함께 전달하고 관계를 일관되게 표현 |
| `fields[...]` | 필요한 필드만 선택해 불필요한 전송 감소 |

참고: [JSON:API 공식 규격](https://jsonapi.org/format/)

## 2. 요청 및 성공 응답

### 요청: API별 DTO 직접 전달

현재 공통 본문 메타데이터가 필요하지 않으므로 요청을 별도로 감싸지 않는다.

- 인증 정보: HTTP 헤더
- 멱등키: HTTP 헤더
- 본문: API별 DTO

### 성공: `ApiResponse<T>`

```json
{
  "code": "DOMAIN-HTTP-NNN",
  "message": "요청이 성공했습니다.",
  "data": {}
}
```

공통 응답 생성과 도메인별 코드 관리를 지원하며, 프론트엔드는 `data`에서 결과를 읽고 내부 데이터는 API별 DTO로 처리한다.

서비스 코드는 메시지 대신 결과를 식별하기 위한 값이다. 프론트의 분기 처리는 변경될 수 있는 문구가 아니라 `code`를 기준으로 한다.

예외 처리:

- 페이지네이션 목록: `data`에 목록과 다음 조회 위치를 포함한다.
- 전체 개수: 필요한 경우에만 제공한다.
- 본문이 없는 `204`: 공통 JSON 응답을 적용하지 않는다.
- 로그인 리다이렉트·파일 전송: 각 HTTP 흐름에 맞는 방식을 사용한다.

## 3. 오류 응답 방식 검토

HTTP 상태 코드만으로는 구체적인 실패 원인을 구분하기 어렵기 때문에, 오류 응답에는 식별 정보와 사람이 읽을 수 있는 설명이 필요하다.

| 사례 | 오류 표현 |
| --- | --- |
| GitHub | `message`, 검증 오류의 `errors`, 세부 코드 |
| Stripe | `type`, `code`, `message`, `param` 등 |
| Google API | 상태·메시지와 `ErrorInfo`의 `reason`, `domain` 등 |

RFC 9457은 HTTP 오류 응답을 위한 표준이며, JSON 표현에 `application/problem+json`을 사용한다. 오류 유형·요약·상태·상세 설명의 의미를 정의하고 서비스별 확장 필드도 허용한다.

| 비교 | 자체 오류 형식 | RFC 9457 |
| --- | --- | --- |
| 필드와 의미 | 팀이 직접 정의 | 표준 의미 사용 |
| 서비스별 정보 | 자체 필드로 설계 | 확장 필드로 추가 |
| 요청·성공 응답과의 관계 | 별도 설계 가능 | 기존 요청·성공 응답을 유지하며 적용 가능 |

참고: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)

## 4. 오류 응답 최종안

오류 응답은 RFC 9457 구조를 따르고, `DOMAIN-HTTP-NNN` 형식의 서비스 코드 `code`를 확장 필드로 추가한다.

```json
{
  "type": "https://example.com/problems/invalid-request",
  "title": "잘못된 요청",
  "status": 400,
  "detail": "요청 값이 올바르지 않습니다.",
  "code": "COMMON-400-001"
}
```

| 적용 규칙 | 이유 |
| --- | --- |
| `type`을 오류 유형의 주 식별자로 사용 | RFC 9457의 식별 규칙 준수 |
| `code`를 서비스 오류 코드로 사용 | 기존 코드 체계와 프론트의 결과 식별 방식 유지 |
| `type`·`code`·HTTP 상태를 공통 오류 정의에서 함께 관리 | 값 불일치와 컨트롤러별 응답 차이 방지 |
| `title`·`detail`은 설명에 사용 | 문구 변경이 프론트 분기에 영향을 주지 않도록 함 |
| 실제 HTTP 상태와 본문의 `status`를 일치 | HTTP 처리와 본문 해석의 일관성 확보 |
